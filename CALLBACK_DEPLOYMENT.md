# Static application callbacks

Deploy the matching vobiz_system_call and vobiz_click_to_call code before changing Vobiz.
Use the Inbound Callback Token saved in the target site's Vobiz Settings.
Do not put a Frappe API key/secret into these URLs.

For dev-sr.butest.tech, configure POST for all three application callbacks:

- Answer: https://dev-sr.butest.tech/api/method/vobiz_system_call.api.webrtc.answer?token=YOUR_INBOUND_CALLBACK_TOKEN
- Hangup: https://dev-sr.butest.tech/api/method/vobiz_system_call.api.webrtc.hangup?token=YOUR_INBOUND_CALLBACK_TOKEN
- Fallback Answer: https://dev-sr.butest.tech/api/method/vobiz_system_call.api.webrtc.fallback?token=YOUR_INBOUND_CALLBACK_TOKEN

Remove the legacy cmd query parameter. Review and retire the legacy WebRTC
Server Scripts after verifying their application/endpoint dependencies. Do not
change another application's callbacks or disable scripts while calls depend on them.

The static hangup handler accepts only uniquely matched managed call_uuid records.
It ignores unknown IDs, ambiguous matches and nonterminal progress events.
Ordinary core/mobile calls continue to use the per-call callbacks generated by
the core router. Keep generated Dial action/callback URLs and credentials intact.
Fallback fails closed with Hangup XML; it does not retry routing or release a
reservation before terminal evidence arrives.

Verify the deployed app revision, run the appropriate migration/cache/restart
steps for the hosting environment, and reload agent consoles between calls.
Test inbound two-way audio beyond one minute, caller hangup, agent hangup,
repeat End Call after termination, and unavailable-agent/fallback behavior.
Verify final status, end time, agent reservation, and eventual CDR synchronization.
The no-audio issue is not considered resolved until this controlled test passes.

These changes are local; this document does not record a remote deployment.
